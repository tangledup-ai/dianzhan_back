## 一、审批流与账务安全

### 1.1 「场地费退款」审批误把租金分期标成已付款
- **现象**：一笔场地费退款审批通过后，系统同时把该场地方某期租金标成了"已付款"。
- **原因**：`apply_payment_links` 用子串匹配 `"场地费" in biz`，"场地费退款"命中了付款分支。
- **修复**：退款分支只回写押金退还后直接 `return`，绝不联动租金分期/电费台账。
- **效果**：退款审批只退押金，不再产生虚假的付款记录。
- **文件**：`backend/app/repositories/approval_repo.py`
- **提交**：见"审批流安全加固"批次（2274e12 之前的本地修改，随用户部署上线）

### 1.2 审批单没有状态机，终态还能继续操作
- **现象**：已通过的审批单可以再次"通过"（重复回写付款状态）；通过后再"驳回"，已回写的付款状态不撤销，账实不符。
- **修复**：`act_on_request` 增加"必须是审批中"校验；小程序端 approve/reject/transfer 同步补齐。
- **效果**：终态审批单无法再被操作，杜绝重复回写和账实不符。

### 1.3 审批人可以冒名（填个名字就能替别人审批）
- **现象**：Web 端审批操作人默认写死"陈总"且是可编辑输入框；后端只记录不校验。
- **修复**：后端从登录用户取操作人（忽略请求体传入的名字）；校验"当前登录人 == 当前节点配置的审批人"，不匹配返回 403；前端操作人改为只读显示当前登录用户。
- **注意**：**审批流程节点里配置的审批人必须是真实用户姓名**，配成"老板"这类角色名会被 403 拦下。
- **文件**：`approval_repo.py`、`api/approvals.py`、`api/mp_approvals.py`、`src/pages/Approvals.tsx`

### 1.4 没配审批流程时默认"申请人自审"
- **修复**：改为自动找平台里 role=boss 的账号作为审批人；找不到才报错，提示先配置流程。

### 1.5 分红有三个绕过审批流的后门接口
- **现象**：`/approve`、`/reject` 可把未结算分红直接置为已通过/已驳回，完全绕过审批流；驳回后无法重新提交（死锁）。
- **修复**：删除 `/approve`、`/reject`（前端本就未使用）；`/settle` 保留但只允许"已通过 → 已结算"；`submit` 允许"已驳回"重新提交；已进入审批/发放的分红禁止删除。
- **文件**：`api/dividends.py`、`src/api/dividends.ts`

### 1.6 场租月台账漏数据隔离
- **现象**：股东账号可通过 `monthly-ledger` 看到全部场地的租金收付。
- **修复**：补 `scope_landlord_ids` 过滤 + 月份格式校验。
- **文件**：`api/rent.py`

## 二、主体归属模型统一（重要口径，改动前必读）

> 详见 [2026-09_主体归属模型速查.md](./2026-09_主体归属模型速查.md)

### 2.1 模型确定：报税主体以电表为准
- **背景**：同一个场地方、同一个品牌下的电表可能分属不同报税主体（用户 2274e12 提交"拆分同一场地方同一品牌的关注不同公司主体"）。品牌方合同上再放"收付款主体"会把整个品牌设成同一个主体，与电表级归属冲突。
- **确定口径**：
  1. **电表**（meters.entity_id）是主体归属的唯一真相；
  2. **品牌方合同不再携带主体**（表单移除选择器、保存时置 null、Excel 导入强制 null）；
  3. **场地合同保留**收付款主体（它是"电表未指定主体时的默认继承来源"，也是场地成本的付款方）；
  4. 归属链：**合同上选的主体 → 电表主体 → 未指定主体**；收入按"场地+品牌"电表柜数分摊，成本按场地电表分摊。
- **落地位置**（均已实现，改主体相关代码前先对照）：
  - 合同页：品牌合同按柜数比例拆到各主体名下显示，标注"（分摊 x%）"；未归属的进"未指定主体"组；
  - 公司主体页：场租视图同样分摊归属 + "未指定主体（待归属）"分组；
  - 股东页看板（station_board）、首页/预警分组（alerts）、场租页（rent）：归属链回退到电表主体；
  - 主体损益表（entity_monthly）、首页明细（monthly_detail）：按柜数分摊（原有）。
- **提交**：623e714、fce8fcd、46e4bc6、9a1986b、ec015c8

### 2.2 品牌方合同"承担场地成本"提示误导
- **现象**：凤凰巷已有场地合同，填品牌合同时显示"暂无场地合同"。
- **原因**：承担成本 = 场地月租 ÷ 场地计费电表数 × 本合同电表数；该场地没关联电表时分母为 0，与"真没有场地合同"混用同一文案。
- **修复**：两种情况分开提示——"该场地暂未关联计费电表，无法分摊（去智慧电表关联后自动计算）"。
- **提交**：a1e842e

### 2.3 编辑电表无法切换报税主体
- **现象**：电表已关联主体 A，编辑想换成 B，报"该电表已关联其他公司主体"。
- **原因**：旧拦截把"换主体"当成"一表挂多主体"防——但 entity_id 是单列，换主体天然是替换。
- **修复**：移除拦截；同时支持解除关联（置空）。
- **提交**：6fe2d4e

### 2.4 各页面主体归属回退链统一（漏网之处）
- **问题**：合同全部未选主体后，股东页看板（station_board）、首页预警分组（alerts）的场地方主体仍只按合同 entity_id 取 → 全部落"未指定主体"。
- **修复**：归属链统一为"场地合同主体 → 其他合同主体 → 电表主体（按电表数取多数）→ 未指定主体"；顺带修了原查询 MAX(entity_name) 不按优先级取值的隐患。
- **文件**：`api/overview.py`（station_board）、`api/alerts.py`
- **提交**：9a1986b

## 三、合同拆期规则重做

### 3.1 拆期算法从"日历月切桶"改为"合同周年日推进"
- **现象**：12 个月年付合同（2025-09-06~2026-09-06）被切成"2025-09-06~2026-08-31 + 6 天尾巴"两期，且每期金额无脑给"月租×期长月数"——6 天的尾巴也收一整年租金 20,999.04。
- **确定口径**（用户确认）：
  1. 期限正好凑成整周期 → 每期金额自动算（月租×期长月数）；
  2. 期限比整周期多出一段 → 多出的尾期**有区间但金额留空**，用户在分期列表手动填（不自动折算）；
  3. 期限连一个整周期都不够 → 也建一期，金额留空手填。
- **修复**：`_split_periods` 改为按合同周年日推进（`_add_months`，月末自动对齐）；`_period_amount` 对被截止日截短的期返回 NULL。
- **效果**：12 个月×半年付 → 2 期各 3600 无尾巴；7 个月×半年付 → 期1 自动 3600 + 尾期（1 个月）留空；不足一周期 → 一期留空。
- **提交**：71c8aad → ff6bfd5 → 6e26e85（三步演进，最终口径见上）

### 3.2 分期列表支持补填金额
- **修复**：金额留空的期次显示"填金额"按钮，行内输入保存；重建分期时**保留用户已填的金额**不被冲掉。
- **文件**：`src/components/ContractSchedule.tsx`、`contract_schedule_repo.py`

### 3.3 表单实时拆期预览 + 保存确认
- **修复**：填完合同起止 + 付款方式后，字段下方实时显示"将拆成 N 期：第1期 xx~xx、第2期 xx~xx（不足整期，金额留空待手填）"；保存时若有不足整期的尾期，弹窗确认。
- **文件**：`src/pages/Contracts.tsx`（splitPeriodsPreview 与后端算法一致）

## 四、生产部署问题

### 4.1 新建电表 400（生产）
- **现象**：本地正常，生产新建电表 400。
- **原因**：生产库是旧版建的表，`init_database()` 只跑 `CREATE TABLE IF NOT EXISTS` 不补新列，且整份 SQL 单事务执行——任何一条失败全部回滚，旧表永远缺 `entity_source` 等新列。
- **修复**：新增 `schema_sync.sql`（纯增量幂等补列）+ `database.py` 逐条执行、单条失败不中断；生产库已手动补齐并验证。
- **提交**：1c9426e
- **教训**：`migrations/` 目录的迁移 SQL 不会随代码自动执行，结构性新增应同时进 schema_sync。

### 4.2 生产环境数据说明
- 生产 PG 容器为**多个软件共用**，只允许对本应用的库做只读检查和纯增量结构变更；
- 生产数据（合同等）为准，本地为开发数据（会被"远程覆盖本地"脚本冲掉）；
- 数据同步脚本：`db_backups/sync_remote_to_local.py`（单向：生产→本地）。

## 六、股东分红口径（2026-09-06 用户确认）

### 6.1 分红基数按配置自由组合
- **口径**：股东/介绍人分红配置的基数按配置自由组合——**绑定品牌 → 该品牌的收入/利润；绑定主体（未绑品牌）→ 该主体的收入/利润；均未绑定 → 整场地**。绑定品牌但当月该品牌无在期合同/电表时，该股东本期基数为 0（不参与），不再错用整场地数字。
- **原因**：同一场地方的股东分红情况多样——有的按整场地收入、有的按利润、有的只参与某个品牌；旧逻辑绑定品牌的股东仍按整场地基数算（brand 只用于显示）。
- **修复**：`_calc_shareholder_dividends` / `_calc_business_dividends` 的基数选择：brand → entity → 整场地，绑定品牌但缺失时基数为 0。
- **提交**：89535d0

### 6.2 季/半年/年分红改为周期内各月累加，每期金额透明
- **口径**：结算月金额 = 周期内各月收入/利润**逐月累加** × 比例（不再是"结算月当月 × 倍数"）；每月明细通过 `cycleDetail` 字段返回；非结算月金额仍为 0；预估模式仍显示单月（前端"核算明细"弹窗已有逐月行，结算金额 = 各月之和，闭环）。
- **实现**：`_cycle_months`（周期月列表）+ `_cycle_base`（逐月累加，`_cycle_sum_depth` 防递归）；商务分红与股东分红一致。
- **验证**（六甲临时季度+利润分红10%配置，验证后已删）：结算月 -843.97 =（7月 -3189.71 + 8月 -3236.20 + 9月 -2013.79）× 10% ✓；预估单月 ✓；非结算月 0 ✓。
- **提交**：89535d0
