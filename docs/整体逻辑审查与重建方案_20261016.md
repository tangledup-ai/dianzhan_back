# 整体逻辑审查与重建方案

> 审查日期：2026-10-16
> 范围：仓库当前 `main` 分支代码、数据库初始化/迁移脚本、前后端页面与现有设计文档。
> 目的：给后续重建或分阶段优化提供一份可执行的业务基线。本文是静态代码审查；没有连接生产数据库，也没有运行应用或测试，因此不会把历史迁移报告中的数据库现状当作当前线上事实。

## 1. 结论摘要

项目已经实现了相当多的业务能力，尤其是电表平台数据同步、人工实际值、共享表分摊、合同期管理、场地级电费差额、场租/分红计算等。当前仍有需要分阶段收敛的财务账务能力。

> 本文记录修复前审查结论。2026-10-16 后续已直接修复电费场地汇总、米表关联过滤、合同生效期校验、类别权限及分红保护等问题；详情见 [电费台账与数据权限修复](2026-10_%E7%94%B5%E8%B4%B9%E5%8F%B0%E8%B4%A6%E4%B8%8E%E6%95%B0%E6%8D%AE%E6%9D%83%E9%99%90%E4%BF%AE%E5%A4%8D.md)。下文“发现”类段落是修复前基线，不代表这些问题仍全部存在。

建议保留现有业务事实与有效数据模型，停止继续横向叠加功能，先完成下列四项收敛：

1. **建立单一运行事实**：Docker 运行的是 Python/FastAPI + PostgreSQL，但 README、根目录 `api/`、`db/schema.ts`、Drizzle 配置仍留下 Node/Hono + MySQL 的模板和历史实现痕迹。先明确唯一运行入口、数据库、部署与迁移流程。
2. **修正账务口径及计算边界**：台账生成当前把“场地损耗”和“共享表未分摊差额”揉到一个差额行里；这与 V5 已确认口径不同。把应收、应付、人工修正、税额、成本/利润计算收敛到可重算的独立计算层。
3. **把权限从列表过滤升级为服务端授权**：现有角色大体只有“股东只读”和“其他人都可访问/修改”；财务的电表类别隔离没有一致地覆盖场租、合同、分红、状态修改、用户与第三方账户配置等写接口。
4. **账务从状态字段升级为可对账流水**：电费和场租页面虽可切换“已付款/已到账”，但这不能表达分次收付、实际金额、收付日期、银行/票据凭证、差额和冲销。结账、更正、收付款应分别建模，并保存当时采用的合同/读数/税率快照。

**不建议推倒重来数据库或直接删除旧列。** 优先用新账务模型承接新月份，历史记录经核对后迁移；保留当前数据和回滚能力。

## 2. 本轮发现的高风险问题

### P0：财务数据隔离并未实现为完整的权限边界

- 修复前 `backend/app/main.py` 的中间件只验证 token，并阻止股东写操作；本轮已加入管理员写权限限制、合同权限、同步权限和类别受限总览保护，并在主要电表、台账、分红接口加入范围检查。仍应逐个 API 复核默认拒绝策略。
- `backend/app/infra/auth_scope.py` 的财务范围只在部分电表/台账读路径生效。`scope_landlord_ids()` 对 finance/finance_supervisor 返回全量场地；标签范围需要各 API 主动额外处理。
- 多个敏感写接口没有场地/类别授权校验。例如电费状态更新 `backend/app/api/electricity.py` 的 `PUT /{record_id}/status` 没有接收当前用户；分红配置、分红新增/提交/结算/删除也存在未统一校验范围的路径（`backend/app/api/dividends.py`）。基础档案、用户管理、第三方平台账户配置同样主要依赖“已登录”，没有管理员角色限制（`backend/app/api/directory.py`）。
- `/api/sync/trigger` 对任意已认证后台用户开放，可触发全量或指定同步；这会消耗第三方平台有限额度。

**建议权限规则**：所有 API 默认拒绝；由后端统一依赖解析 `user + role + landlord scope + meter category scope + action`。每个读、写、导出、批处理操作都在服务层授权，不能依赖前端隐藏按钮或页面过滤。电表范围应直接以 `meters.category_code` 为准，场地级汇总只能聚合授权范围内的电表；成本与合同若不属于电表类别，应另行明确归属规则，不能因场地拥有某类型电表就隐式泄露全部品牌/合同/财务数据。

### P0：电费“损耗”计算口径与已确认文档不一致

`backend/app/api/electricity.py` 台账生成处的 V5 注释写明损耗是 `final_kwh - ref_kwh`（最终付场地方电量减场地全部电表实际量），但实际代码约在 869–875 行使用 `final_kwh - site_pay`；`site_pay` 是已生成的品牌应付电量合计。于是共享表没有分摊的电量也被记进“场地损耗”，两个不同概念被合并，可能使差额行金额和场地损耗重复或错算。

**必须拆成两个字段/概念**：

- 场地损耗：`场地最终结算电量 - Σ场地所有电表实际电量`，归我方承担，不分给品牌。
- 共享表未分摊差额：`单块共享表整表电量 - 该表已分摊给品牌的电量`，单表提示/我方承担。
- 品牌应付只按品牌自身电量算；场地方应付只按最终结算金额/电量算。台账展示可分别列示，但不能将“品牌已分配的应付总和”当作场地参考电量。

另外，当前代码只在 `loss_kwh > 0` 时生成差额行。真实结算量小于表计量时应如何处理（负损耗/冲减/异常待核）需要统一规则，不能静默忽略。场地级只录最终金额时，当前从金额除以单价反推电量会丢失实际账单金额与“电量×合同价”的差别；应允许金额覆盖并保留差异。

### P1：共享品牌“绑定清单”没有形成独立、可维护的业务事实

`meter_shared_brand_bindings` 有表和仓储函数，但当前调用链 `bind_brands()` 是保存分摊时按分摊行顺带建立绑定。没有看到独立的品牌绑定维护入口；按“该月应有品牌名单”检查漏录的规则也未落实为可见告警。因此“绑定”和“本月有金额的分摊”仍可能混为一件事，无法表达“本月绑定但暂时无电费/漏填”。

**建议**：绑定清单有独立维护接口与历史生效区间；每月生成前对绑定清单与分摊行做完整性检查。分摊允许金额、电量、主体或柜数为空的业务状态必须由字段语义表示，不能把空行等价于未绑定。

### P1：收付款只有单一状态，不能支撑真实财务对账

电费记录直接使用 `pay_status` / `collect_status`；场租主要从合同分期计划与状态字段展示。这样的布尔式状态不能准确表达分期实付、部分付款、一次付款覆盖多账期、退款、手续费、差额、票据、银行流水和撤销。用户要求的“手动选择收付款情况”可由此实现，但后续财务核对无法追溯状态为何变更、实际收付金额是多少。

**建议**：应收/应付账单与收款/付款流水拆表。账单保存应收/应付金额和核算来源；流水保存实际金额、日期、支付方式、凭证、操作者；多条流水可核销同一账单，退款/冲销为反向流水。页面的“已到账/已付款”由已核销金额自动得出，允许人工标注“账外已结清”时必须填原因并记审计。

### P1：合同、金额快照与历史重算混杂

修复前合同校验把场地合同限制为每场地一份，并且数据库重叠约束把合同类型混在一起。本轮改为允许连续合同版本，按合同类型/品牌/主体判定生效期重叠；对应数据库变更见 `backend/app/migrations/2026_10_contract_period_constraints.sql`。台账生成会按现有合同重算；已核对账单版本/更正机制仍需后续建设。分红刷新现已保护申报中、已通过、已结算记录，不再静默覆盖。

**建议**：草稿/未核对月份可重算；已核对账单不得被上游编辑静默改写。重算生成新版本并对比差异；确认更正后保留旧版、原因、字段差异、操作者、时间。合同和电表配置变更以生效日期/月份控制，不能改写历史快照。

### P1：第三方同步额度与同步结果不够可靠

`backend/app/main.py` 的 `/api/sync/monthly-kwh/status` 通过 `meter_readings.synced_at` 统计当月“调用次数”，实际统计的是读数行数量而非外部 API 请求次数；因此剩余额度展示不可信。同步任务按日/周期调度，且 `sync_meters.py` 中多个账户逐个调用；没有看到按账户、接口、时间窗口统一的额度预留/限流器。额度判断若依赖读数行，重试、空结果、批量一调多表时都会计错。

**建议**：建立 `integration_call_log`，每次请求在发出前原子占用额度，记录账户、接口、时间、结果、重试、请求关联 ID、影响读数；达到额度时跳过并告警。同步只写平台原始/标准读数快照，不覆盖人工实际值；相同来源数据幂等更新，失败可重试并有可查询日志。

## 3. 架构与工程状态

### 3.1 运行入口需统一

- 当前 `docker-compose.yml` 构建 `backend/`，服务端是 Python/FastAPI + PostgreSQL，运行端口 3001。
- 根目录 `README.md` 仍是 React/Vite 模板说明；`api/boot.ts` 是另一套 Hono/tRPC 服务入口；`package.json` 构建 Node 服务、`Dockerfile` 期待 `.env` 和 Node dist；与此同时 `Dockerfile.frontend` 构建独立前端。
- 根目录 `db/schema.ts`、Drizzle 配置、MySQL 依赖与 `.env.example` 的数据库说明，与当前 Python/PostgreSQL 部署不一致。

这让新贡献者难以判断哪套代码会进入生产，也使数据库模式变更容易只改到“死路径”。应在 README 中明确唯一部署拓扑；未使用的旧入口标记为 legacy 并从默认构建剔除，或正式恢复为唯一入口，避免双栈同时保留。

### 3.2 数据库迁移需要唯一历史和发布机制

当前有初始化 SQL、`schema_sync.sql`、大量手工迁移脚本、V2→V5 迁移脚本，以及 Drizzle 迁移目录。生产结构是否等于任何单一 schema 文件无法由代码库保证。部署时应由一个有序迁移工具管理版本、事务、锁、校验和回滚策略；数据库约束作为最终一致性防线，迁移执行结果必须可见、失败必须阻止发布。

### 3.3 计算逻辑应从 API 路由拆出

`backend/app/api/electricity.py` 承担路由、数据库查询、取价、共享分摊、生成快照、损耗行及更新记录等多种职责，且单文件已超过千行。需要按账务规则拆成 `ReadingService`、`ElectricityCalculation`、`LedgerGeneration`、`PaymentReconciliation` 等纯/应用服务；API 只校验输入、授权、调服务并序列化响应。

金额统一使用数据库 `NUMERIC/Decimal`，不要在多处把金额转 `float` 后分别取整。每一条账单需要保存计算输入快照、公式版本、分项金额和舍入规则，以便月结后复现。

## 4. 建议的目标业务模型

### 4.1 主数据

- **场地方/场地**：建议“合作方”和“物理场地”分开建模；目前 landlord 同时承载老板、合同地点、台账归属。一个场地方可有多个地点，若当前业务确定始终一对一，可先保留现状并避免重复名称被当作同一地点。
- **品牌方**、**报税主体**、**员工/用户/角色**：独立主档。主体是收入开票/纳税归属，不是成本承担对象。
- **电表**：`meter_id` 内部主键；业务表号可编辑；第三方设备标识单独且唯一；所属场地、类别 `category_code`、表型 `is_shared`、品牌关系、互感器倍率、生效/退役时间为显式字段。换表必须新增表档案，不复用旧表身份。
- **柜子**：带品牌、场地、电表（允许暂缺）、进场/退出时间；按月快照柜数，平摊成本只使用该快照。

### 4.2 抄表与人工修正

把第三方原始值和财务认可值分开：

1. `meter_reading_observation`：平台、手工录入、导入分别保留原始表码/区间/电量/采样时间/请求批次/来源账户，不覆盖旧观察值。
2. `meter_monthly_actual`：每表每账期唯一的采用值，包含开始/结束表码与日期、计算用电量、倍率快照、人工覆盖值、修正原因、确认人和时间。
3. 采用规则显式记录 `selected_observation_id` / `override_kwh`，历史账单引用被采用版本；平台补数不会覆盖人工认可值。
4. 普通表品牌归属唯一；民用表无收入对象；共用表通过月度品牌绑定和月度品牌分摊产生多条品牌电量。

“表码差、倍率、实际电量”必须明确一个统一公式：`实际电量=(结束表码-开始表码)×倍率`，如人工直接填写实际电量则不得再乘倍率。当前读取/录入路径存在手工实际值与人工表码差的语义差异，应在表单、API、字段名和快照中统一。

### 4.3 合同与费率

保留“场地合同（我方应付）”和“品牌合同（我方应收）”两类，但每份合同应具有：合同方、场地、品牌（收入合同必填）、生效起止日、续签/替代关系、租金规则、电费单价、租金/电费各自税务配置、付款周期/账期规则、押金规则、附件和审计历史。

单一账单行必须明确命中哪份合同和哪段费率。按自然月结算且月中变价时需要可配置的按天/按用量切分规则，不能用“取第一份合同”或静默选择。不同合同的费率、币种/税费口径、免租期、押金不得塞在同一覆盖字段中。

### 4.4 月度台账与对账单

电费台账至少有两侧账单，按自然月生成但保留实际抄表日期：

- **品牌应收**：场地 × 品牌 × 主体 × 月；电量来自普通表读数 + 已绑定共享表分摊；价格命中品牌合同；税额和含税/不含税金额独立留存。
- **场地应付**：场地 × 月；参考量为所有表实际电量之和；结算量/结算金额允许财务覆盖；成本行可有多电表明细，但不把场地损耗分摊到品牌。
- **租金应收/应付**：独立租金台账，支持固定月费、按柜、年费折月、进退场首末月按天、手工调整；每条结果保存计费基数和合同来源。
- **平摊成本**：单独展示在内部经营分析中，不作为品牌应收；规则为场地租金成本 × 品牌柜数 / 所有有品牌柜数。
- **损耗与未分摊差额**：一个场地月损耗行 + 每共享表月未分摊差额提示/行，口径分别保存。
- **核对**：产生可分享/导出的一版核对单，记账期、版本、应收/应付方、明细、口径、生成时间；双方确认后标记已核对。已核对账单不能被普通重算覆盖。

### 4.5 收付款、税票和结账

- `receivable_payable`：应收/应付账单及当前未结金额。
- `cash_transactions`：收款、付款、退款、押金收退、冲销；记录方向、金额、时间、主体、对象、方式、参考号、凭证和操作者。
- `settlement_allocations`：把一笔现金流水核销到一张或多张账单，支持部分核销和一次支付结多期。
- 发票状态独立于收款状态：待开、已开、红冲等；不能把“开票”和“到账”合并。
- `period_closing`：按月 × 方向 × 往来对象结账；结账时保留账单版本与数据哈希。历史差错通过更正单增加新版本，要求原因和审计，不通过回滚/覆写旧值处理。

押金是资产/负债而非收入/成本；只有没收、退回或冲抵时才产生相应会计影响。

### 4.6 分红

分红应基于明确的“场地分红池”，先计算收入、真实场地成本、运营费用、退款/损失、商务分红，再按场地股东配置分配。配置支持全场地或品牌范围、生效区间、分红基数/比例、结算周期和主体；同一股东可在不同场地有不同配置。

分红预估与分红结算必须是两个动作：未完成月份仅给预估；结算周期完成后生成带输入快照的结算单。上游账单更新不静默重写已审批/已支付分红；更正后产生补发/追回差额。公式必须覆盖品牌专项股东、全场股东、商务分红、周期累计、负利润、税费、退款，禁止在全局可变对象上设置 estimate 模式。

## 5. 页面与功能建议

| 页面 | 页面职责 | 关键动作 |
|---|---|---|
| 总览 | 只看汇总经营指标和异常，不承载改账 | 选择期间、看待抄/待核/逾期/超额度告警 |
| 场地/品牌/主体档案 | 维护业务主数据与关系 | 禁止硬删除已被合同/账单引用的主档，改为停用 |
| 合同中心 | 合同版本、费率、期限、押金和付款周期 | 新签/续签/调价/附件/变更比较；检查生效期冲突 |
| 电表中心 | 电表主档、类别权限、普通/共享属性、第三方设备映射 | 换表退役、新建、授权范围内导入/同步 |
| 抄表工作台 | 平台原始值、人工实际值、倍率、异常对比 | 选择本月采用值、填写修正原因、确认读数 |
| 共享表分摊 | 月度品牌绑定、应收金额/电量、主体和柜数 | 绑定变动当月生效；显示缺行/超读数/未分摊差额 |
| 电费台账 | 可按场地方或品牌查看应收、应付、税额、差额和利润 | 展开品牌/电表明细；生成核对单；记录收付流水 |
| 场租台账 | 仅展示应收/应付场地费、计租基数、内部平摊成本 | 按品牌/场地视图，收付、核对、退款 |
| 运营费用 | 月 × 场地费用及可选主体分摊 | 录入凭证、保存成本归属规则 |
| 分红 | 股东/商务配置、周期预估、正式结算 | 预览输入基数、确认结算、审批、支付和更正 |
| 收付款流水 | 全部收款/付款/退款/押金核销记录 | 上传凭证、分配到账单、处理差额 |
| 结账与更正 | 月度结账状态、账单版本、变更对比 | 锁定版本、申请更正、审计导出 |
| 用户与权限 | 用户、角色、场地和电表类别授权 | 最小授权、角色模板、权限变更审计 |
| 同步中心 | 外部账户额度、运行记录、失败/待映射设备 | 手动触发需授权并先校验额度，失败可重试 |

每个台账列表都应能切换“按场地方 / 按品牌方”；点击汇总行展开合同、品牌、电表、计算过程和收付款核销。场地费、电费使用分开的账单与核对按钮，避免用户误以为总利润核对等于双方账单核对。

## 6. 重点设计规则（建议作为产品验收标准）

1. 一块电表只有一个类别；共享属性是独立布尔/枚举，类别不参与算法判断。
2. 普通表最多关联一个品牌；民用表无品牌；共享表多个品牌通过带生效月份的绑定清单关联。
3. 每表每月最多一个“已采用实际读数”版本，但保留所有平台观测、导入和人工修订版本。
4. 电表平台同步不能覆盖人工实际值；缺读数、无场地、无合同、倍率异常、共用表漏分摊都必须成为可追踪异常。
5. 每场地每月成本侧以场地合同和财务确认的最终结算量/金额为准；每品牌收入侧仅以对应品牌电量和品牌合同计算。
6. 场地损耗、表内未分摊差额、品牌应付、我方内部平摊成本分别展示和入账。
7. 金额以 Decimal/NUMERIC 计算，按账单规则统一取分；不能在各页面自行重算同一笔金额。
8. 合同、柜数、主体、倍率、税率的变更有生效时间；历史账单使用生成时快照。
9. 到账/付款源于流水核销；开票独立；押金不进入利润；退款在发生月用反向流水冲回。
10. 财务用户只能读取/更改授权类别所涵盖的电表和明确授权的下游账单；跨类别场地的汇总只提供授权数据的部分汇总，并清楚标注“部分范围”。
11. 任何重算都输出变更预览；结账后必须通过更正流程更新，并保留旧账单、原因和操作人。
12. 第三方请求额度按外部 API 请求计数，不以读数行数代替。

## 7. 建议分阶段实施

### 阶段 A：先止住数据风险

- 收敛唯一后端运行路径和部署说明；强制从环境注入 JWT 密钥、第三方密钥、数据库连接，启动时校验而非采用可预测默认值。
- 建立统一授权依赖，把角色、场地、类别校验应用到所有详情、写入、导出、批处理和配置接口；第三方同步设为有权限的管理员操作并受额度闸门保护。
- 修复场地损耗与共享表差额的公式分离；处理负差额/直接录金额的规则；生成器失败要返回明确状态，禁止保存成功却吞掉账务更新错误。
- 输出当前数据库结构/数据质量审计：孤立电表、无场地/合同/主体、重叠合同、倍率异常、历史人工值、共享表绑定与分摊缺行、金额不守恒。

### 阶段 B：稳定单月账务闭环

- 建立统一期间服务和 Decimal 计算服务；合同费率命中、人工值采用、税费、日租、损耗、分摊只在服务层实现。
- 账单生成改成版本化、幂等、可预览；重算先展示差异；已核对账单生成更正版本。
- 为电费和场租增加对账单/结账状态；把收付款流水、部分核销、退款从状态字段拆出。
- 补齐共享表绑定管理与完整性告警，确保品牌覆盖清单和电量分摊是独立数据。

### 阶段 C：租金与分红财务化

- 固化品牌应收租金、场地应付租金、柜数月快照、按天首末月、手工调整和押金的口径。
- 股东/商务分红改为分红池、周期累计、审批/支付快照；重算只生成差额更正。
- 页面统一按场地/品牌双视图，能从汇总追到合同、读数、倍率、单价、公式和付款流水。

### 阶段 D：数据迁移与淘汰旧实现

- 先迁移并对比历史月份，不覆盖旧库；抽样核对账单金额与纸面/Excel 原始凭证。
- 以月份为单位逐步切换新账务读写；确认后只读归档旧账。
- 删除 legacy 字段、旧 API、旧 schema 和失效页面前，先完成引用扫描、数据库快照及回滚演练。

## 9. 待确认的业务决策

以下不应由开发者擅自猜测，建议在重建前形成书面决定：

1. 场地最终账单金额和“最终用电量×合同单价”不一致时，利润按实际金额还是合同公式金额？差额应单列为议价/调整还是场地损耗？
2. 最终结算量小于电表参考量时，负损耗冲减成本、作为供应商折让，还是阻止结账待复核？
3. 普通表的付款电量是否总等于其实际读数？共享表表内未分摊差额应单列成本还是只作为提示？
4. 电费/场租税率代表价内税、销项税率还是实际缴税比例？品牌合同价格输入是税前还是含税？不同合同可能需要不同答案。
5. “报税主体只用于收入”是否仍为最终规则？场地租金成本、运营费用和利润分红如何在多主体间展示或申报？
6. 同一物理场地是否可能有多个场地方业主/多份场地合同，或场地方名下多个独立场地？这决定 landlord 与 site 是否要拆表。
7. 月度分红在周期未结束时仅预览还是允许预支？周期中合同/流水变化如何回溯？
8. 财务角色除电表类别外，还需要哪些独立权限（查看合同、改读数、核对、登记付款、维护配置、导出）？
